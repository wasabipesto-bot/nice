# Review of `dev/mo-wide-b65` (`0b6e22e1..a7ea3890`): wide tops list and shared parents (2026-11-27)

**Verdict: merge with fixes.** Reading the code, I found no way for these three commits to lose a candidate silently: every partly filled plane or capacity case I could construct fails an account. The two fixes I would require are both small: (1) a test that checks the shared-parents path against an independent reference, survivor for survivor, including the range's clipped ends (today nothing does), and (2) one line that checks the compact list's own count `tstat[2]` against the scan's `tstat[0]`.

Reviewer: independent, reading only (`git show a7ea3890:…`, `git diff 0b6e22e1 a7ea3890`). Nothing built, run, changed, pushed or commented. The tooling denied nothing. Line numbers refer to `common/src/midout/gpu_wide.rs` at `a7ea3890` unless another file is named.

## Findings, ranked

Ranking: (A) a candidate can be lost silently, (B) a failure is not loud, (C) robustness, (D) quality. **I found nothing in class A.** The highest findings are test gaps (B/C) that would let a future class-A defect in the shared path go unnoticed outside the sampled check.

### 1. (B, test gap; fix before merge) No test checks the shared path against an independent reference

- **Where:** `wide_whole_small_bases_vs_brute_force` (l. 4681–4750) and `wide_slices_equal` (l. 4505–4650). Both go through `run_slice` (l. 4728, and l. 3959 `queue_prep(.., false)`), which is **always unshared**. The new `wide_field_parent_sharing_is_exact_and_loud` (l. 4931) compares shared against unshared only. It does so on `WCounts` (8 counts per slice), not on survivor sets, over 130 of the 4,225 slices of one b65 field (77777), and that field is probably interior to the range (not checked).
- **Scenario:** the narrow path's slice test has a `share` case that builds the shared list and compares the slice n for n with the CPU (`gpu.rs` l. 4712, 4776–4790, `MIDOUT_SHARE8`). The wide port has none. Suppose a later change makes `wanc_kernel` and `whist` disagree in a way that keeps the counts equal, or a key/digit-order slip that only shows at some bases or shapes. Then nothing but production's sampled check (one slice per field, survivor *count* only for the shared run, l. 4071–4085) would see it. The brute-force test, the one test that reaches the range's clipped first and last slices, never runs with sharing.
- **Smallest fix I would accept:** a variant of `wide_whole_small_bases_vs_brute_force` that runs the whole range through `search_field_wide` (field path, sharing on). Each field should hold several slices per key, so that `keys.len() < pips.len()` and `build_anc` really runs. Then assert the union of checked n equals brute force, and the nice list too. The shapes with `k − 2 > f0` in that table, (13; 0,3), (17/18; 1,4), (19; 0,4), (20/24; 1,4), (25; 2,5), would exercise it. Alternatively port `MIDOUT_SHARE8` to `wide_slices_equal`: `build_anc(&[anc_key(pip)])`, then the slice with `shared = true`, n for n against the CPU. Either takes seconds to minutes on any card.
- Also assert in the new test that the lists were **used**, not only built: `nl >= 1` (l. 4983) is true even if `anc_for` never matched, in which case shared = unshared trivially. For example, record `hn < nrf` for every slice in the test.

### 2. (B, one-line fix before merge) `tstat[2]` (the compact list's count) is never read back

- **Where:** `finish_group` reads `s[0]` and `s[1]` of `tstat` (l. 3731–3745). `wtops2` iterates `min(tstat[2], cap)` (l. 2025).
- **Why it is mostly covered today:** `A_T2_PLACED` counts the entries that `wtops2` iterated, which is `min(tstat[2], cap)`. `check_slice` requires it to equal `ntops = tstat[0]` (l. 3865). `tstat[0]` comes from the scan of `segc`, which every certifying lane increments itself, independently of the ballot. So an under-count of `tstat[2]` is loud, and so is an over-count up to the cap.
- **The hole:** suppose `tstat[2] > cap` with `tstat[0] == cap` exactly. Then placed = cap = ntops, and the check passes. But `tstat[2]` was over-counted, so the slots in `[0, cap)` are not all written. `wtops2` would then place records left in `tc` (persistent, `self.tc`) from the previous slice, and a real top would be dropped. This needs a broken ballot *and* an exact hit on the cap, so it is unlikely, but it costs nothing to close.
- **Fix:** read `tstat[2]` with the other words and `ensure!(s[2] == s[0])`.

### 3. (B, test gap) No fault shows that the sampled check catches an error confined to the shared path

- **Where:** new test l. 4931ff. `F_SKIP_ANC` (l. 2861) is loud through `build_anc`'s *cubes done* account at the field's start (`a[0] == grid`, l. 3187). That is a real account, not only the sampled check, so the brief's question is answered: loud by an account.
- **What is not shown:** a `wanc_kernel` that lists a wrong set while its own counts stay consistent (a logic error, the shared analogue of `F_BAD_PARENT`) is visible only to the sampled check. The production code does compare the right things. `wide_sample_compare` compares `in_field`, the shared field run's per-slice survivors (pushed from `finish_group` of the shared loop), with `wide_cpu_slice`, which is pure CPU. The device rerun is `run_slice`, which is unshared (`queue_prep(.., false)`, l. 3959). So the check is independent of the lists. But no test runs `cpu_check: true` with a shared-path fault.
- **Smallest test:** a fault bit in `wanc_kernel` that drops roots `rf % 997 == 0` from `ok` before the ballot (consistent counts). Run the new test's field path with `cpu_check: true`, and assert `Err` from the sampled check's *field-run* comparison (the "field run counted survivors" message), not from its rerun.

### 4. (C, outside the diff but the brief's question) Partly filled planes: the new appends fail loudly. The pre-existing `wtops5` append would not.

My analysis of the three ballot appends, for lanes inactive at the ballot (a short plane, or lanes left in a different *tangle* after the `if` blocks on a driver without maximal reconvergence) and for lanes finishing in different rounds:

- **`wtops1`** (l. 1852; ballot l. 1974, atomic l. 1984). The loop bound `j0` is uniform per cube, so all lanes run the same number of rounds and none finishes early. Ranks come from the real `UNIT_POS_PLANE` and the ballot, so a smaller-than-reported plane (16 of 32) is handled correctly. If the plane is *wider* than compiled (w = 32 on a 64-lane plane), `n` misses `bl[1]` and lanes 32+ collide, but `tstat[2]` is then short. If lanes are inactive or split off from lane 0, their `n` is never added to `tstat[2]`, and the lanes that did not run under-count `A_T1_EXAM`. **In every case `tstat[2]` (or `A_T1_EXAM`) differs from the independent `tstat[0]`/`l5n[0]`, so "wtops2 tops placed" or "wtops1 valid parents examined" fails.** I found no case where the count is right but slots collide. There is no plane-width check in `wtops1`, and none is needed for soundness.
- **`wanc_kernel`** (l. 1415). It has the plane-width check (`acc8[3]`). Any split that leaves live lanes outside lane 0's tangle under-counts *roots examined* (`plane_sum(live)` by lane 0, l. 1466), which must equal `nroots` (l. 3190). That is loud. A tail cube splits only by `live`, and the non-live lanes have `ok = false`, so it is harmless.
- **`wtops5`** (l. 1738–1841, **not changed by this branch**, and the list that `wtops1` now walks). It has the same ballot append with **no plane check and no count independent of the ballot**: `l5n[0]` is the ballot's own sum, and `l5n[1]` counts only cubes. If a plane's certifying lanes run their ballot without lane 0, they write at base 0 over other planes' entries. Their count is never added, and `wtops1` then examines exactly `l5n[0]` entries (consistent), so **a valid prefix, and so its tops, would be lost silently**. This needs a non-reconverging driver; NVIDIA and current AMD reconverge at structured merges. The base-64 `tops5` probably shares the pattern (not checked). **Suggested fix (separate PR):** an independent per-lane count of `ok` (a shared-memory atomic per lane, added by thread 0) in `l5n[2]`, required to equal `l5n[0]`. The same applies to `whist`'s `A_H_CERT`, which comes from a ballot summed by lane 0 and so shares the tangle exposure with `lcnt`.

### 5. (C) Base 66–70 and wave64 have not run on this branch; memory and fallback

- `wtops1` is now compiled per plane width (`w` comptime, new `w > 32` branch). `wanc_kernel` is new. Neither has been compiled or run at w = 64: all of the write-up's tests ran on an RTX 3060 (w = 32). The wide slice test's compile-only path (`MIDOUT_FORCE_W`, l. 4523) never calls `build_anc`, unlike the narrow path's (`gpu.rs` l. 4744). **Settle by** a compile-only run with `MIDOUT_FORCE_W=64` on lavapipe after adding a `build_anc` call to that path, and a run of the new test on the 9070 XT through Vulkan.
- Memory at 66–70, my estimate (not measured): with the tops cap of 16M, `tc` + `tps` take 1.0 GB, replacing about 2.5 GB of per-prefix arrays at b68. The lists take about b × 3/8 × nrf × 4 B, roughly 1.3 GB at b68 if nrf is near 13M (a guess from b65's 10.9M). So roughly neutral. But the lists are never freed and there is **no fallback to unshared** if their allocation fails or a list exceeds `anc_cap`: every field would then fail loudly. Not a loss, but a card that ran b66–70 before could stop producing results. **Settle by** one field at b68 or b70 with peak memory, on the smallest card meant for those bases.
- `wide_oom_is_loud` (l. 5034) runs one slice through `wgroup`, so it never reaches `build_anc`'s list allocation. A field-path variant would show that a failed list allocation is loud. I expect it is: the kernel would not run, and `a[0] == grid` would fail. I could not confirm this by reading, because it depends on CubeCL's out-of-memory behaviour.
- `build_anc` requires `n > 0` for every key (l. 3202). A key with no valid ancestor fails the field instead of giving an empty list. That is impossible at b ≥ 64 but possible at small bases (relevant to the test in finding 1, where it would show up as a false failure).

### 6. (D) Accounts and hygiene

- `wanc_kernel`'s "roots certified = listed" (`a[2]`, l. 3196) is not independent. `sh[1]` and `cnt[0]` both add the same lane-0 `n` (l. 1457, 1469), so they can differ only if a cube stops part-way. The doc comment (l. 1410) says "apart from the list's own count". The account that actually protects the list is *roots examined* (`a[1]`). I would fix the comment, or make `a[2]` a per-lane count of `ok`.
- The narrow path clears the shared keys at the end of the field as well (`gpu.rs` l. 4222); the wide path only clears them at the start (l. 4234). This is harmless as far as I can see: a list is a pure function of (key, the join's roots), so a stale list with a matching key is still exact, and no other production caller calls `queue_slice`. But it is a divergence from the code it ports. A `keys.clear()` after the loop would match the narrow path.
- `WideJoin` has `&self` methods behind mutexes. Two fields running at once on one join would share `tc`/`tps`/`t5list`/the lists. This is pre-existing (`tm`/`tv`/`t5list` before), and `route.rs` runs one field at a time, so it is only worth a doc line.

## The brief's questions, answered

1. **Compact append:** sound, and fails loudly under partly filled or split planes (finding 4). Every lane runs the same rounds (`j0` is uniform per cube). Drops, duplicates and overwrites all change a count that is checked against the independent `segc` scan. The one gap is finding 2.
2. **Capacities:** tops: past the cap, records are not written, `tstat[0] > caps.tops` is checked for every head ticket (l. 3731) on the field path and in `run_slice`, and the shared and unshared paths run the same check. Lists: `n <= anc_cap` (l. 3202), checked once per field at build time for every key. Timing stops (`stop < 6`) skip `finish_group`'s checks, but `search_field_wide` refuses them (l. 4129). `rank_of` does not check the tops cap; this is pre-existing and harmless, because the same slice is also run and checked in the field.
3. **Stale data:** `tc` and `tps` persist across slices. `wtops2` reads `[0, min(tstat[2], cap))` with `tstat` fresh per slice (l. 3274). `wtdigz` reads `[0, min(tstat[0], cap))` of `tps`, all written by `wtops2` when the counts agree. A stale read therefore needs the count mismatch that the accounts catch (finding 2 is the only exception). Lists persist across fields, keyed and exact (finding 6). The write-up's explanation of the `F_SKIP_TOPS` dump is right: the old `wtops2` walked the fresh `t5list` but tested the per-prefix `tv` left by the previous slice's `wtops1`. Now `tstat[2] = 0`, so it places nothing. The fault fails on the same first check, "wtops1 valid parents examined".
4. **Sharing exactness:** I checked the containment claim. `parent_w(.., k − 1)` sets digits 0..f0−1 from `rf` and f0..k−3 from the key, and tests digits 0..k−3 of r² and r³ for 2(k−2) distinct values. Those digits depend only on r mod b^(k−2), and their distinctness is necessary for the full depth-(k−1) test. `whist` writes only certified parents, and its record, key and class use the slice's full `pipd` and `pip`. So `whist` over the list produces the same set of parents as over every root (order is arbitrary in both). The key is all of digits [f0, k−2) (`anc_key`, l. 3110), and the digit order of `d8` matches `pip_digits`. Clipping at the range's ends acts only in `wtops1` and the expansion, never on parents, so the clipped first and last slices and the padded coordinate cannot break the sharing. The lists depend on (key, roots) only: no other field's or coordinate's data enters them. `whist`'s account follows the list length (`hn`, l. 3289/3866) and proves the grid covered the list. Completeness of the list rests on `wanc`'s *roots examined* account.
5. **The sampled check:** independent (finding 3). The shared field run's per-slice survivor count is compared with the CPU, and the unshared device rerun is compared n for n with the CPU.
6. **Tests:** the new test compares slice by slice (group 1), on real b65 data, but counts only, 130 slices, with no range ends (finding 1). The slice test's new tops comparison compares **contents**: sorted `(unit, lead, mask)` vectors, so duplicates and drops both fail (l. 4556–4593). It does not compare the prefilter digits `ttq`/`ttqh` or the segment, but those are covered by the survivor sets compared n for n. The fault tests' assertions are unchanged; only the printed `F_SKIP_TOPS` dump differs, as explained in answer 3.
7. **Other bases:** base 64 on the wide path gets sharing by default (the write-up says so). Production b64 is the narrow path (`route.rs`), so this affects only tests and benches. For bases 66–70 and w = 64, see finding 5. `ANC_LISTS = MAXB = 70` covers every base; a field with more keys falls back to unshared.
