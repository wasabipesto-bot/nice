## What → replace the "Work distribution" bullet with

- **Work distribution.** Each plane takes the next entries of the survivor list, one per lane, from a counter, asking
  for the next ones before it works on these. The lanes that run a take decide it among themselves, so it does not
  rely on full planes or on a lane 0 (Vulkan promises neither, and wgpu does not ask for full subgroups): on planes of
  at most 32 lanes, one ballot gives the lanes taking part, their count, each lane's rank and the leader (the lowest
  of them), which takes that many entries and passes the start on by a shuffle; on wider planes, an exclusive scan and
  a sum of 1, and the leader's start as a sum. The counter is a fifth word of the batch's `ran` buffer, which the
  cube counts do not read. The kernel also counts the entries it checked and sums their indices into two more words,
  and the host compares both with the list after every batch (see Soundness). The kernel launches 2048 cubes, more
  than a GPU holds at once at its 39–47 registers (at 47, b62 and b64, 5 cubes per SM: a 3080 holds 340, an H100 660); cubes that start after the list is
  exhausted exit at once. The old grid-stride loop over 1024 cubes left a tail on every device.

## Soundness → replace the section with

The check computes the same base-b digits of n² and n³ by another route, and decides as before: n is nice iff the digits of n² and n³ (exactly s2 + s3 = b positions; the top limbs' digit counts are fixed per field, so no leading zero is ever counted) are all distinct.

- **n.** H·b^k2 + w6·b^f0 + r0 = n, with H = ⌊n / b^k2⌋: w6 = P mod b^(k2 − f0) is what both top kernels write to word 6 (the join's prefilter reads the same word), and r0 = n mod b^f0 is the list entry's. P − w6 is a multiple of b^(k2 − f0) = 2^z·o, so ((P − w6) >> z)·o⁻¹ mod 2^32 is H whenever H < 2^31, which holds on every field the join takes (H < b^5); the tests' smaller windows, where H reaches about 2^40, take it apart by 16-bit chunks instead. The probe mode rebuilds n from its limbs and the device test compares it with the list's n.
- **No overflow.** Every column of n² or n³ has at most ⌈L/2⌉ products of limbs below b², plus a carry below ⌈L/2⌉·b², so it is below ⌈L/2⌉·(b⁴ + b²) < 2^31 at every shape the join runs (`CheckShape::new` checks it per field: at most 7·(64⁴ + 64²) ≈ 1.2·10^8 here).
- **Exact quotients.** For d ≥ 3 not a power of two, m = ⌈2^(32+s)/d⌉ with s = ⌊log2 d⌋ is below 2^32, and e = m·d − 2^(32+s) lies in (0, d). Then x·m / 2^(32+s) = x/d + x·e / (d·2^(32+s)), and the second term is below 1/d whenever x·e < 2^(32+s), which holds for x < 2^31 because e < 2^(s+1). So `mul_hi(x, m) >> s` = ⌊x/d⌋ for every x < 2^31. Every quotient's input is below 2^31: columns and chunks below 2^28, limbs below b², and r0, w6 and a narrow H below 2^31 (checked per field). A power-of-two base uses shifts. A host test checks the bound for every divisor b and b² at bases 3–64. It also checks the worst element of every block of d across each input range the kernel uses (the quotient is monotone and never below the true one, so that element decides the block). An opt-in test (`NICE_TEST_CHECK_EXHAUSTIVE=1`) checks every x < 2^31 for every divisor.
- **The gate only drops non-nice n.** A repeated digit among n² and n³'s low digits is a repeated digit of n² and n³.
- **Every survivor is checked exactly once, on any plane.** A take's participants are the lanes that run its plane operations together, however many there are and whether or not lane 0 is among them. With a ballot (planes of at most 32 lanes, the same switch the FD kernel's append uses), the ballot's first word is exactly that set on every backend (inactive lanes' bits are clear); each lane's rank is the popcount of the participants below it, the participant of rank 0 takes as many entries as there are participants with one atomic, and the start reaches the others by a shuffle from that lane, which is active. On wider planes (64- and 128-lane, which the ballot's first word cannot hold), the rank is an exclusive scan of 1 and the count a sum of 1, both over the active lanes, and the start is the sum of the leader's value and zeros. Either way the counter is cut into disjoint, consecutive ranges, each handed to as many lanes as it holds entries, one each. A lane leaves the loop only when its own take starts at or past the list's length, so every entry below the length lies in a range that some take started below the length, and the lane of the matching rank in that take checks it. Nothing depends on `PLANE_DIM` or on the plane being full. The old hand-out (lane 0 took `PLANE_DIM` entries, lane i checked the i-th) skipped the missing lanes' entries on a partly filled plane: on CUDA with a 100-thread cube (a last warp of 4 lanes) it left 896 of about 4,040 entries unchecked, and with 48 threads 1,008, while the counter ended where it would have with full warps. CUDA and Metal give full planes for 256-thread cubes; Vulkan does not promise it.
- **Per backend.** The ballot form uses a ballot, the lane index and a shuffle with a lane index computed at run time: `__ballot_sync`/`__shfl_sync` on CUDA, `subgroupBallot`/`subgroupShuffle` in WGSL (naga requires a constant index only for `subgroupBroadcast`), `OpGroupNonUniformBallot`/`OpGroupNonUniformShuffle` in SPIR-V, `simd_ballot`/`simd_shuffle` on Metal. The shuffle is new to these kernels; wgpu enables subgroups only on Vulkan devices that support subgroup shuffles, so every device that runs the join through wgpu has it. The wide form uses the exclusive scan and sum the FD kernel's append already uses; on HIP these are lowered over all 64 lanes, which 256-thread cubes always fill.
- **The host checks that every listed survivor was checked.** Every lane counts the entries it checked and sums their indices; the kernel adds both to two more words of `ran`. After each batch and each partition re-run has passed the cube counts, the host compares them with the list: `min(checked, list_cap)` entries and the sum of 0 … listed − 1 (mod 2^32). The index sum catches an entry checked twice standing in for one skipped, which a count alone would pass. A mismatch is an error and the field fails (the client submits nothing for it); it is not treated as a layout the device refused, since a smaller layout would not help, and it never yields a field with fewer candidates. Two test-only modes must fail a field, in a pass of batches and in a partition's re-run: one leaves the list's first entry unchecked (the count is short), and one checks the first entry in place of the second (the count is right and the index sum one short). A host unit test covers the comparison itself, including an overflowed list and the sum's wrap mod 2^32. The test modes are comptime bits that only tests set: the production kernels' generated CUDA and WGSL are the same as without them.
- **What tests the check.** Every hit comparison in the suite but b10's [47, 100) is on a range with no nice number, so a check that rejected too much would pass all of them. The device test therefore compares the kernel's own output with the CPU for every survivor, in three test-only modes. Count mode skips the gate and writes four words per list entry: the number of distinct digits of n² and n³ (against the client's `get_num_unique_digits`), whether the entry passes the gate (against its definition), and the 64-bit digit mask. Gated mode writes the same words with the gate applied as the hits mode applies it, so the divergent rest of n³ runs only in the lanes that pass, and it runs on a grid of one to three cubes, so every plane takes work from the counter many times. Probe mode writes every n rebuilt from its limbs. Each runs on 256-thread cubes and on 100-thread cubes (a partly filled last plane on every plane width), and on CUDA also in the wide form; a second test runs a synthetic list of every shape on 256-, 100- and 48-thread cubes, in both forms on wgpu and in the ballot form on CUDA. Every run checks that each entry was checked exactly once (the kernel's own count and index sum) and that the work counter ends one take per lane past the list. On CUDA a partly filled warp runs on one cube only: CubeCL's CUDA backend takes a thread's lane as its position in the grid modulo 32, which is its lane only where every cube is a multiple of 32 threads (production's are 256), so 100-thread cubes after the first get wrong lanes on any kernel. Each run also records the smallest take: on CUDA the test asserts takes of 4 and 16 lanes for 100- and 48-thread cubes, and on lavapipe the 100-thread cubes' last subgroups take 4 of 8 lanes. No nice number is known above base 10, so the hits path meets a real hit only at b10's 69 (`check_all`); the gated mode covers that path's control flow on every survivor that passes the gate.
