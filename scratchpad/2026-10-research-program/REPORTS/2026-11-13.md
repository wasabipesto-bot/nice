## Addendum, 06:35 UTC: please do not merge #251 yet

The soundness audit finished first. **It found no way for today's production code to lose a
candidate unnoticed.** It did find a real gap in my own open PR #251: the new check kernel hands
out work one GPU subgroup at a time and assumes every subgroup is full. CUDA and Metal guarantee
that; Vulkan does not. On a device that ran a partly filled subgroup, some listed candidates
would never be checked and the host would not notice. I read the kernel and agree with the
audit. No measured device is known to be affected, but the tests that ran on your card cannot
see a skipped check, so that is weak comfort.

- I tried to mark #251 as a draft and comment on it; the harness refused both, so I sent you one
  ntfy instead and did not work around the refusal. **If you would rather the PR say so itself,
  convert it to draft, or allow me to.**
- A fix is in progress on a second rented box: reproduce the skip on a real device, hand out
  work by each lane's rank among the lanes that exist, and have the kernel count what it checked
  so the host can verify it. It lands as new commits on the same branch, with an independent
  review before I call the PR ready again.
- #255 and #256 are not affected.

One proposal from the audit, for you to accept or decline (not built): the join's two
counters are exact functions of the field, the same on every device. NiceMark already records
them on every box it benchmarks and compares them with nothing. Pinning the CPU's values per
scenario would turn the benchmark into a known-answer test on every device that runs it; it
would have caught both the #222 race on the M4 and the Metal miscompile.
