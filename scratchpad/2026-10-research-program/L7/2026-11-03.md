## B. Targeted questions

### B1. Shared-memory bank conflicts gathering a 64-word table by 32 lanes with arbitrary indices

No source found addresses this *exact* shape (64-word presence table, 32 lanes,
each lane ORing 12 arbitrary-index words per 32-element chunk, 8 chunks/batch) —
this looks like a project-specific combination, not a published benchmark. What's
available is a set of generic, well-documented techniques, each only a partial
fit:

- **Padding / swizzling** — the direct cause here ("digits d and d+32 share a
  bank") is the classic stride-32-divides-64 aliasing case covered by every
  bank-conflict writeup found (Lei Mao, "CUDA Shared Memory Swizzling"; the
  "Decoding Swizzle<B,M,S>" visual guide; the ROCm CK-Tile blog's XOR-swizzle for
  AMD LDS; and the peer-reviewed "Padding-Free Bank Conflict Resolution for
  CUDA-Based Matrix Transpose Algorithm"). Padding (insert dead words to break the
  period-32 repeat) and XOR-swizzle (permute the index before addressing, no
  wasted memory) both exist specifically to kill this fold. **Caveat**: all of
  these are demonstrated for *regular, statically-known* access patterns
  (transpose, strided matrix tiles) — not for a gather with fully data-dependent,
  per-lane-arbitrary indices into a 64-word table, which is the actual case here.
  Swizzle still works for arbitrary indices (it's just an index permutation
  function, index-independent of data), so it transfers in principle; it just
  isn't validated anywhere found at this specific table size/lane count.
- **Table replication (histogram privatization)** — "replicate the LUT across
  more banks" is a named, real technique (GPU histogram-privatization literature,
  surfaced via search, not an arXiv paper — general-knowledge/blog level). For a
  64-into-32 table this would mean storing two offset copies so a lane's bank
  depends on which copy it reads, cutting worst-case conflict multiplicity. Doesn't
  eliminate conflicts for *arbitrary* per-lane indices (you can't statically know
  which copy avoids a collision when the index is data-dependent), only reduces
  expected conflict degree — not validated at this scale by any source.
- **Warp shuffle instead of shared memory** — this is the technique most likely to
  actually dodge the bank-conflict model entirely, not just reduce it: the medium
  write-up "Warp Shuffle vs Shared Memory: Which Is Faster?" and NVIDIA's own
  guidance describe distributing small per-lane tables into registers (here: 2
  registers/lane, since 64 words ÷ 32 lanes = 2) and using `__shfl_sync` with a
  computed source-lane (`idx % 32`) plus a register-select (`idx / 32`) to gather
  — the shuffle crossbar isn't bank-addressed the way shared memory is, so the
  d/d+32 aliasing problem doesn't exist in that model. This is the strongest
  candidate of the four, but **unverified**: no source found benchmarks
  shuffle-based gather against shared-memory gather at exactly this 64-entry,
  12-of-64-OR-per-lane workload; it's a transfer of a general pattern, not a
  measured result.
- **Bit-sliced/transposed representation** — this is literally what this
  project's own 10-29 sweep (Section B, "bit-sliced transposed OR-column")
  already proposed for the adjacent join-kernel problem, not something
  independently found in the literature for this LUT-gather case. Worth noting it
  generalizes here too (transpose the 64-word table into per-bit-position columns,
  combine via ballot rather than per-lane gather) but it's internal prior art, not
  new external confirmation.
- 16-bit-half processing: no technique beyond "process low/high 32-word halves as
  separate passes with an offset to avoid same-cycle aliasing," which is just
  padding/swizzle applied specifically to the 2×32 fold — same caveat as above.

**Net for B1**: four candidate techniques, none validated at this exact
scale/shape by any source found; swizzle and warp-shuffle are the best-evidenced
general techniques and are cheap enough to prototype directly rather than keep
researching.

### B2. SWAR distinctness test / sub-one-shift-per-digit presence-mask build

No direct hit. Searched Lemire's blog corpus (parsing hex/digit strings, SWAR
control-character detection), the "0x80.pl" bit-trick notes, and PDEP/PEXT
literature:

- **Lemire's SWAR posts** ("Parsing short hexadecimal strings efficiently,"
  "Packing a string of digits into an integer quickly," "Detect control
  characters... using SWAR") all demonstrate the right *shape* of trick — extract
  or compare several packed sub-fields using one multiply/mask/compare instead of
  one operation per field — but none test *distinctness among k packed symbols*,
  which is a different predicate (existence of a repeat, not a field's value).
  **No existing instance of this exact test was found.**
- **0x80.pl, "How to detect if all bytes in a SIMD register are equal"** is the
  closest adjacent trick in spirit but is literally the opposite test (all-same
  vs. all-distinct) and doesn't extend directly — checking "any repeat" generally
  needs an O(k²) pairwise-compare network or a scatter-based presence test;
  checking "all equal" is a single reduction. Not transferable as-is.
- **PDEP (parallel bit deposit, x86 BMI2)** is the right *primitive* for "build a
  64-bit presence mask from packed digits with less than one shift per digit" —
  one `pdep` call scatters k one-bits to k arbitrary positions in one instruction,
  which is exactly the stated goal — but it's **x86-only**; an NVIDIA developer
  forum thread found in this search ("PDEP and PEXT functionality for CUDA")
  confirms there's no native CUDA equivalent as of that thread. If B2 is meant for
  GPU kernel code this doesn't transfer directly; if it's for host-side/CPU
  preprocessing it's a strong, well-documented fit (Mula & Lemire's "SIMD parallel
  bits deposit/extract" note covers the AVX-512 `VPDPBUSD`-adjacent variants too).
  Given the project's GPU focus, flag this as **CPU-only, unverified GPU
  applicability**.
- **Bioinformatics k-mer literature** (2-bit-packed base sequences, bit-parallel
  Hamming-distance-≤1 tests) addresses *distance between two k-mers*, a different
  problem from *internal distinctness within one k-mer* — not a match, despite
  initially looking promising from the query framing.

**Net for B2**: no off-the-shelf algorithm found for either half of the question.
The only concrete transferable primitive (PDEP-style scatter) is CPU-only;
nothing found solves the GPU-side mask-build or the distinctness test faster than
the straightforward approach. This reads as a genuine gap rather than a missed
search term — the predicate is narrow enough (bounded-k distinctness over small
alphabets) that it may simply not have a dedicated literature.

  external literature, and shouldn't be counted as answering the question.
- **No external paper found** describing finite-difference stepping of
  polynomial-value digit arrays across a stride-bˢ prefix step (as opposed to a

  Searched directly for this combination; results returned only the project's own
  PR, general Wikipedia finite-difference background, and unrelated pandigital
  enumeration papers (already known, e.g. arXiv:2403.20304, 1610.09830,
  2112.00444 — none of which discuss stepping method, only counting results).
- **Interval certification of leading digits of x² and x³ faster than converting
  one endpoint**: no paper found. Checked "Exact Constructive Digit-by-Digit

  relevance that reading it in full wasn't worth the budget, but this is

**Net for B3**: no external prior art found for either half. The stride-bˢ
finite-difference question and the interval leading-digit certification question
both look like genuine gaps — narrow enough, and specific enough to this search's
exact computational structure, that they may not have been studied outside this
project.

week's three targeted questions. What did come out:

- **B1**: four named, real techniques (swizzle, padding, table replication,
  warp-shuffle-as-register-LUT) are legitimate candidates, with warp-shuffle the
  best bet given it sidesteps the bank model rather than mitigating it — but none

- **B2**: a real negative result — no literature match for bounded-k distinctness

  on-target primitive (PDEP) doesn't run on GPU hardware. Don't keep searching for
  this one; it looks like a genuine literature gap rather than a search-term

- **B3**: also a real negative result, and it surfaced a reminder that this
  project's own PR #221 already explores *unit-stride* finite differences for
  digit arrays — worth checking against the stride-bˢ case directly rather than
  via more literature search, since the literature isn't going to answer a
